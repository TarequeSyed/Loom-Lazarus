# Requirements Document

## Introduction

This feature delivers the Benchmark_Suite: a deterministic, headless, network-free evaluation library in `src/benchmark`, with command-line entry points in `scripts/`, that produces credible, reproducible measurements of Loom Lazarus detection and restoration. It is the fourth of five specs (domain, detection, restoration, benchmark, UI). The UI spec is the consumer of the browser-readable reports this feature produces.

**Core principle.** Every number in a report comes from a recorded run, carries its dataset version, seed, split, sample size and component versions, and is accompanied by an uncertainty estimate or an explicit statement that none could be estimated. The Benchmark_Suite never invents an accuracy figure, a restoration-time saving, or a historical-photograph result. Where a measurement was not made, the report says "not evaluated" or "not conducted" with a reason.

**What the Benchmark_Suite measures.**
- **Detection track:** a rendered card image goes through `detect`, and the per-cell result is compared with the known instruction ground truth.
- **Restoration track:** a clean deck is damaged at cell level through the domain's neutral damage hook, `runInference` proposes values for the masked cells, and the proposals are compared with the known truth. A comparison against simple baselines uses the same inputs and the same splits.
- **End-to-end track:** damaged card images go through `detect`, `mapDetection` and `runInference`, and the final proposals are compared with the known truth.
- **Real-photograph track:** evaluated only where licensed reference data exists, reported separately, and never merged with synthetic numbers.
- **User comparison:** a protocol for comparing manual-only and assisted restoration time. The default report states "not conducted".

**Synthetic results are results about the generator.** The synthetic datasets are generated by this project under an unverified Garín profile. Synthetic accuracy does not predict accuracy on historical cards. Pattern families with known repetition or symmetry make the restoration priors helpful by construction. Results on those families show that the mechanism works. They are not evidence of how common repetition or symmetry is in historical decks (assumptions R1, R2).

**Builds on approved contracts.** The Benchmark_Suite reuses these names without redefining them. From the domain: `MachineProfile`, `Deck`, `Card`, `Cell`, `RawObservation`, `Provenance`, `Bit`, `ActionId`, `createDeck`, `createCard`, `bitmapToDeck`, `deriveDamagedDeck`, `DamageFn`, `RandomFn`, `compareCells`, `deckEquals`, `readIndexToGrid`, `gridToReadIndex`, the canonical JSON conventions, and the `Result` shape. From detection: `detect`, `DetectionResult`, `DetectionParameters`, `mapDetection`, `CardDetectionRecord`, `compareDetectionToTruth`, and the pure metric functions it exports for this spec. From restoration: `runInference`, `RestorationInput`, `RestorationConfig`, `Hypothesis`, `Abstention`, `PriorMeasurement`, `CalibrationRecord`, `maskCell` and the masking contract, and the minimal JSON dataset format read by `scripts/restoration-tune.ts`.

**Dependency direction.** `src/benchmark` may import the public indexes of `src/domain`, `src/vision` and `src/restore`. None of those three may import `src/benchmark`. `src/ui` may import `src/benchmark`. Scripts in `scripts/` may import any of them.

**Verification status of the card format.** The Garín format values in `jacquard-card-format.md` are NOT verified against Rodas Lorente et al. (2025), https://doi.org/10.1007/s11042-025-20917-9. The Benchmark_Suite takes the Machine_Profile as input, copies its verification markers into every report, and lists its dependence on unverified items under "Assumptions requiring verification".

**Process rule for thresholds.** This document fixes no accuracy, calibration, runtime-saving or coverage threshold. Requirement 18 defines how thresholds are set from recorded preliminary experiments. Until a threshold is recorded in the threshold register, its status is "not set".

**Scope boundaries.**
- In scope: dataset generation, pattern families, damage models and levels, splits, ground-truth separation, the leakage guard, metric definitions, baselines, calibration data, reports, tables, static browser reports, execution profiles, the preliminary-experiment process, the user-comparison protocol, and the error registry.
- Out of scope: the React UI, report rendering, the detector and restoration algorithms themselves, physical loom control, training of learned models, any server or network service, and any claim about historical card prevalence.

## Glossary

- **Benchmark_Suite**: The `src/benchmark` library and its `scripts/` entry points, as a whole.
- **Dataset_Builder**: The component that generates decks, renders images, applies damage and writes a Dataset_Manifest.
- **Benchmark_Runner**: The component that runs evaluation tracks over a dataset and writes a Benchmark_Report.
- **Report_Reader**: The browser-safe component that validates and imports a Benchmark_Report. It uses no Node-only API.
- **Dataset_Version**: A string that identifies one generator configuration and its definitions (pattern families, damage models, damage levels, split rules).
- **Dataset_Manifest**: The canonical JSON file that lists every Family, Item, split role, seed, parameter set, artifact reference and content digest of one dataset.
- **Pattern_Family**: A named rule that generates binary decks with a known structure, for example `periodic` or `random`. Each carries a Structure_Label.
- **Structure_Label**: For each Structural_Prior kind (`repeat`, `symmetry`), one of `helpful` (the structure exists by construction), `non-helpful` (no structure exists) or `partially-helpful` (structure exists with a stated perturbation).
- **Deck_Family**: The set of all items derived from one base design, meaning one Pattern_Family, one base-deck seed and one profile. Every damaged copy, image rendering and damage-level variant of that base design belongs to the same Deck_Family.
- **Family_Key**: The string that identifies a Deck_Family: Pattern_Family identifier, parameter identifier, base-deck seed and profile identifier.
- **Item**: One evaluation unit inside a Family: a clean deck, a damaged deck, or a set of rendered card images, plus its damage description.
- **Split_Role**: One of `tuning`, `calibration`, `held-out` or `test`. Each Deck_Family belongs to exactly one role.
- **Sealed_Test_Role**: The `test` role, whose results are read only after the threshold register is frozen (requirement 10).
- **Damage_Model**: A deterministic function of a seed and a Damage_Parameter set that damages a deck (Cell_Damage_Model) or a rendered image (Image_Damage_Model).
- **Damage_Level**: One of `none`, `light`, `moderate` or `heavy`, each mapping to one Damage_Parameter set per model category.
- **Damage_Level_File**: The versioned JSON file `data/synthetic/damage-levels.json` that holds all Damage_Level definitions and the Occlusion_Cover_Fraction.
- **Occlusion_Cover_Fraction**: A per-Cell_Window coverage fraction. It is the minimum fraction of the area of ONE Cell_Window that a solid occluder must cover before detection must not report that cell as an observed absent hole. It is measured inside a deliberately damaged (occluded) region. It is NOT the fraction of all cells of a card or deck that are occluded, and "about 90% of all cells occluded" is rejected as a starting condition. Its initial value is 0.9 (requirement 7.5 and 7.11). The detection unknown-evidence property reads this value from the Damage_Level_File.
- **Occlusion_Extent**: The Image_Damage parameter `occlusionCoverage` of one Damage_Level. It is the maximum fraction of the readable Cell_Windows of one card that the `occlusion` model may damage (cover by at least the documented overlap fraction). It is separate from the Occlusion_Cover_Fraction (requirement 7.12).
- **Damage_Mask**: The ground-truth record of which cells a Damage_Model altered, stored separately from system inputs.
- **Clean_Ground_Truth**: The undamaged `Deck` (or the instruction bits of a card) from which an Item was derived.
- **System_Input**: Any artifact the system under test receives: a damaged deck, a rendered image, a profile, parameters, Prior_Measurements and a Calibration_Record.
- **Ground_Truth_Artifact**: Any artifact that records true values, Damage_Masks or family information. Never a System_Input.
- **Leakage_Guard**: The set of types, file-layout rules and tests that keep every Ground_Truth_Artifact away from the system under test.
- **Evaluation_Policy**: The documented rule that converts system output into evaluated predictions (requirement 17).
- **Proposal_View**: The set of per-cell values the system proposes without any human review: the effective value of each observed cell, or the rank-1 Hypothesis value of each cell that a Hypothesis covers. A Proposal_View is not an approved deck.
- **Evaluation_Group**: A named set of cells over which one metric is computed, for example `damaged-cells` or `all-cells`.
- **Metric_Value**: Either `{defined, value}` or `{undefined, reason}`. A Metric_Value is never a silent `0` or `1`.
- **Baseline**: A simple, documented, prior-free restoration method evaluated on the same inputs and the same splits as the proposed system (requirement 16).
- **Benchmark_Report**: The canonical, versioned JSON file that holds every Metric_Value, uncertainty estimate, sample size, version stamp and failure-example reference of one run.
- **Browser_Report**: A size-limited Benchmark_Report variant written for static loading by the UI.
- **Threshold_Register**: The versioned JSON file that records each acceptance threshold with the preliminary experiment that set it (requirement 18). Its initial content marks every threshold "not set".
- **Preliminary_Experiment**: A recorded run identified `E-1`, `E-2` and so on, used to set thresholds and parameter values (requirement 18).
- **Execution_Profile**: `quick` (for continuous integration) or `full`, each with documented bounds (requirement 23).
- **Cluster_Bootstrap**: A percentile bootstrap that resamples whole Deck_Families with replacement, using a fixed seed.
- **Reliability_Data**: The per-bin counts, mean confidence and observed accuracy used to draw a reliability diagram.
- **User_Comparison_Protocol**: The documented protocol for comparing manual-only and assisted restoration on the same bounded tasks (requirement 19).
- **Benchmark_Error_Code**: A code in the Benchmark_Suite error registry (requirement 25). The registry uses the domain `Result` shape and does not extend the domain `ErrorCode` union.
- **Component_Stamp**: The recorded interface versions and Implementation_Stamp of the domain, detection and restoration components used in a run.

## Requirements

### Requirement 1: Evaluation tracks and scope

**User Story:** As a researcher, I want separate detection, restoration, end-to-end and real-photograph tracks, so that each claim is tied to the stage it measures.

#### Acceptance Criteria

1. THE Benchmark_Runner SHALL provide a Detection_Track that renders card images, calls `detect`, and compares the result with the Clean_Ground_Truth of the same Item.
2. THE Benchmark_Runner SHALL provide a Restoration_Track that damages a clean deck through the domain `deriveDamagedDeck` hook, calls `runInference` with the damaged deck and no image evidence, and compares the Proposal_View with the Clean_Ground_Truth.
3. THE Benchmark_Runner SHALL provide an End_To_End_Track that renders and damages card images, calls `detect` and `mapDetection` for each card, assembles the mapped cards into a deck, calls `runInference` with the resulting `CardDetectionRecord` values as detection evidence, and compares the Proposal_View with the Clean_Ground_Truth.
4. THE Benchmark_Runner SHALL provide a Real_Photograph_Track that runs only where requirement 11 is satisfied, and SHALL report its results in a section that shares no table, average or summary line with any synthetic track.
5. THE Benchmark_Runner SHALL state in every Benchmark_Report, as a fixed text, that synthetic results measure the system on generated data and do not estimate performance on historical cards.
6. THE Benchmark_Runner SHALL run each track independently, so that selecting one track does not require data or output of another track.
7. THE Benchmark_Suite SHALL measure the proposals of the system and SHALL NOT present a Proposal_View as a human-approved deck.
8. IF a requested track cannot run because a required input is absent, THEN THE Benchmark_Runner SHALL record the track as `not-evaluated` with a reason, and SHALL NOT omit the track from the Benchmark_Report.

### Requirement 2: Pattern families and deck generation

**User Story:** As a researcher, I want pattern families with and without repetition and symmetry, so that the structural priors are tested where they help and where they cannot.

#### Acceptance Criteria

1. THE Dataset_Builder SHALL generate base decks from the following Pattern_Families, each with a documented parameter set and a Structure_Label for each Structural_Prior kind: `periodic` (period `p` in a documented range, row patterns copied at every card distance `p`), `periodic-perturbed` (periodic with a documented fraction of cells flipped), `card-mirror` (card `i` equals card `c - i` for an axis position `c`), `within-card-mirror` (each card satisfies the documented partner mapping), `periodic-and-mirror`, `random` (independent uniform bits with no induced structure), `sparse-or-constant` (bit density within the degenerate margin of 0 or 1), and `bitmap-derived` (decks produced by `bitmapToDeck` from named binary bitmaps such as stripes, checkerboard, diamonds and a seeded noise bitmap).
2. THE Dataset_Builder SHALL label `random` and `sparse-or-constant` as `non-helpful` for both prior kinds, SHALL label `periodic` as `helpful` for `repeat`, and SHALL label `periodic-perturbed` as `partially-helpful` with its perturbation fraction recorded.
3. THE Dataset_Builder SHALL verify the Structure_Label of each generated base deck with an independent check that does not call the restoration Evidence_Test, and SHALL reject a base deck whose measured structure contradicts its label with error `PATTERN_LABEL_MISMATCH`.
4. THE Dataset_Builder SHALL generate each within-card symmetry deck from a partner mapping that the Benchmark_Suite defines and documents itself, and SHALL provide a conformance test that compares that mapping with the partner mapping documented by restoration for the same profile, and SHALL report a difference as a test failure and not as a silent adjustment.
5. THE Dataset_Builder SHALL accept a deck size between 1 and the configured maximum cards per deck, whose default values are set per Execution_Profile in requirement 23 and which SHALL NOT exceed the domain limit of 10,000 cards.
6. THE Dataset_Builder SHALL give every base deck a bit density that its Pattern_Family documents, and SHALL record the measured density in the Dataset_Manifest.
7. THE Dataset_Builder SHALL record in the Dataset_Manifest, for every base deck, the Pattern_Family, its parameters, the base-deck seed, the profile identifier, the Structure_Label values, and the content digest of the Clean_Ground_Truth.
8. IF a Pattern_Family parameter is outside its documented range, THEN THE Dataset_Builder SHALL return error `INVALID_DATASET_CONFIG` naming the parameter and its range, and SHALL generate no partial dataset.
9. THE Dataset_Builder SHALL document that decks generated under `helpful` families establish that the restoration mechanism works, and SHALL NOT present any frequency of helpful families in a dataset as evidence of historical prevalence.

### Requirement 3: Machine profiles used in datasets

**User Story:** As a researcher, I want datasets under both the Garín profile and small generated profiles, so that results can be checked quickly and at the real card size.

#### Acceptance Criteria

1. THE Dataset_Builder SHALL support the Garín profile (51 x 8 grid, 400 readable positions) and generated profiles that pass the domain profile validation with 3 to 12 grid rows and 2 to 8 grid columns.
2. THE Benchmark_Runner SHALL report every metric separately for each profile identifier, and SHALL NOT pool results of different profiles in one Metric_Value unless the report marks the pooled value as pooled and lists its constituents.
3. THE Dataset_Builder SHALL copy the verification markers of the profile into the Dataset_Manifest and every Benchmark_Report.
4. WHERE a profile marks a field `unverified`, THE Benchmark_Report SHALL state that the results depend on that unverified field.
5. IF a supplied profile fails domain validation, THEN THE Dataset_Builder SHALL return error `INVALID_DATASET_CONFIG` with the domain error code and path, and SHALL generate nothing.

### Requirement 4: Clean image rendering and renderer ownership

**User Story:** As a maintainer, I want one clearly owned benchmark renderer that stays consistent with the detection test generator without importing it, so that no circular dependency forms.

#### Acceptance Criteria

1. THE Dataset_Builder SHALL render, for each card of a deck, a clean card image from the Clean_Ground_Truth with a known Card_Quadrilateral, a known hole polarity and a known applied orientation, using a seeded pseudo-random generator and no `Math.random`.
2. THE Benchmark_Suite SHALL own the benchmark image renderer in `src/benchmark`, and THE detection spec SHALL keep its own smaller test generator in `src/vision/__tests__` for unit and property tests.
3. THE Benchmark_Suite SHALL NOT import from `src/vision/__tests__`, and `src/vision` SHALL NOT import from `src/benchmark`.
4. THE Benchmark_Suite SHALL keep the two generators consistent through the Damage_Level_File, whose schema is defined in requirement 7 and which both generators read as data, through a shared documented meaning for each Damage_Parameter name and unit, and through a conformance test in `src/benchmark` that renders clean cards at documented sizes and asserts that `detect` returns Alignment_Status `aligned` and recovers the Clean_Ground_Truth bits of every cell with a documented tolerance determined by Preliminary_Experiment E-1.
5. THE Dataset_Builder SHALL record the renderer version, the image format, the image size in pixels and the rendering parameters in the Dataset_Manifest.
6. THE Dataset_Builder SHALL render images no larger than the detection Intake_Limits defaults, and SHALL encode them in a format that detection supports (PNG, JPEG or WebP).
7. IF a rendered image fails the detection intake limits, THEN THE Dataset_Builder SHALL return error `RENDER_OUT_OF_LIMITS` naming the limit, and SHALL write no artifact for that Item.
8. THE Dataset_Builder SHALL generate the clean image of a card deterministically, so that equal inputs and an equal renderer version give byte-identical image bytes.

### Requirement 5: Cell-level damage models

**User Story:** As a researcher, I want controlled, seeded damage to decks, so that restoration is measured on cells whose true values are known.

#### Acceptance Criteria

1. THE Benchmark_Suite SHALL own these Cell_Damage_Models, each a deterministic function of a seed, a clean deck and a Damage_Parameter set: `random-cells` (a fraction of readable cells masked uniformly at random), `consecutive-run` (runs of consecutive `readIndex` values masked within a card, with run lengths drawn from a documented range), `strip` (a band of consecutive `readIndex` values masked over a range of consecutive cards), and `missing-cards` (all readable cells of selected cards masked).
2. THE Benchmark_Suite SHALL implement each Cell_Damage_Model as a caller-supplied `DamageFn` and a caller-supplied seeded `RandomFn` passed to the domain `deriveDamagedDeck`, and SHALL NOT bypass `deriveDamagedDeck` to modify a deck.
3. THE Cell_Damage_Models SHALL mask a cell by returning a Raw_Observation without value and without hole likelihood, so that the cell appears in the damaged deck with provenance `ambiguous` and no effective value, as the restoration masking contract requires.
4. THE Cell_Damage_Models SHALL provide run lengths both at most and greater than the `shortRegionBound` that the restoration configuration in use specifies, so that both the proposal path and the `REGION_TOO_LARGE` abstention path are evaluated, and SHALL read that bound from the restoration configuration and not hard-code it.
5. THE Cell_Damage_Models SHALL compose in a documented, fixed order, and SHALL record each applied model and its parameters in the Damage_Mask.
6. THE Cell_Damage_Models SHALL leave at least the documented minimum number of Trusted cells in each deck, and SHALL return error `DAMAGE_TOO_SEVERE` naming the limit if the parameters would exceed it.
7. THE Cell_Damage_Models SHALL produce identical damaged decks for identical seeds, clean decks and parameters.
8. WHEN a Cell_Damage_Model runs, THE Benchmark_Suite SHALL leave the Clean_Ground_Truth deck deeply equal to its value before the run.
9. IF a Damage_Parameter is outside its documented range, THEN THE Benchmark_Suite SHALL return error `INVALID_DAMAGE_PARAMETERS` naming the parameter and its range, before any damage is applied.

### Requirement 6: Image-level damage models

**User Story:** As a researcher, I want controlled photographic and physical damage to card images, so that detection and the end-to-end pipeline are measured under known conditions.

#### Acceptance Criteria

1. THE Benchmark_Suite SHALL own these Image_Damage_Models, each a deterministic function of a seed, a clean rendered image and a Damage_Parameter set: `illumination-gradient`, `shadow`, `stain`, `cord`, `patch`, `tear`, `blur`, `noise`, `rotation`, `perspective`, and `occlusion` (a solid-colour cover of chosen cell windows).
2. THE Image_Damage_Models SHALL apply in a documented, fixed order (illumination gradient, shadow, stain, cord, patch, tear, occlusion, rotation and perspective, blur, noise), and SHALL record each applied model and its parameters in the Damage_Mask.
3. THE Image_Damage_Models SHALL record, for each damaging element, its polygon in image coordinates and the set of `readIndex` values whose Cell_Window overlaps the polygon by at least the documented overlap fraction, in the Damage_Mask.
4. THE Image_Damage_Models SHALL leave every card image at or above the detection minimum size and inside the card image bounds after rotation and perspective.
5. THE Image_Damage_Models SHALL produce byte-identical images for identical seeds, clean images and parameters.
6. THE Image_Damage_Models SHALL NOT alter the Clean_Ground_Truth or the clean image.
7. IF a Damage_Parameter is outside its documented range, THEN THE Benchmark_Suite SHALL return error `INVALID_DAMAGE_PARAMETERS` naming the parameter and its range.
8. THE Benchmark_Suite SHALL document, for each Image_Damage_Model, its meaning, its unit and its known simplifications, and SHALL state that these models approximate physical damage and are not a measurement of historical damage.

### Requirement 7: Damage levels, the Damage_Level_File and the damage hook

**User Story:** As the author of the detection and restoration specs, I want damage levels defined once as data, so that all specs read the same definitions.

#### Acceptance Criteria

1. THE Benchmark_Suite SHALL define the Damage_Levels `none`, `light`, `moderate` and `heavy`, with one Damage_Parameter set for the Cell_Damage_Models and one for the Image_Damage_Models.
2. THE Benchmark_Suite SHALL store all Damage_Level definitions in the Damage_Level_File with a `format` marker, an integer `schemaVersion`, a `damageLevelVersion` string and a `source` field that names this spec.
3. THE Damage_Level_File SHALL contain, for each Damage_Level, these Image_Damage fields with units: `blurSigmaPx`, `noiseSigma`, `illuminationGradient`, `perspectiveDeg`, `rotationDeg`, `stainCoverage`, `cordCoverage`, `tearCoverage`, `occlusionCoverage` (the Occlusion_Extent), and the single file-level Occlusion_Cover_Fraction (a per-Cell_Window value, not a per-level share of cells), and SHALL contain for each Damage_Level these Cell_Damage fields: `maskFraction`, `runLengthRange`, `stripWidthRange`, `stripCardRange` and `missingCardFraction`.
4. THE Benchmark_Suite SHALL require, and test, that for each numeric parameter the values are non-decreasing from `none` through `light` and `moderate` to `heavy`, that every parameter of `none` equals zero, and that no two Damage_Levels have identical parameter sets.
5. THE Benchmark_Suite SHALL define the Occlusion_Cover_Fraction as a per-Cell_Window coverage fraction (the minimum fraction of one Cell_Window's area that a solid occluder must cover before detection must not report that cell as an observed absent hole) that is greater than 0.5 and at most 1, SHALL set it at least equal to the detection default `unknownCoverFrac`, SHALL set its initial value to 0.9 (which satisfies all three bounds, provided `unknownCoverFrac` does not exceed 0.9), and SHALL record the preliminary experiment that confirmed it.
6. THE numeric values of the Damage_Level_File SHALL be initial values set in design and confirmed or revised by Preliminary_Experiment E-2, and THE Damage_Level_File SHALL carry the identifier of the experiment that last confirmed each value, or the marker `initial-unconfirmed`.
7. THE Benchmark_Suite SHALL replace the placeholder file `data/synthetic/damage-levels.placeholder.json` with the Damage_Level_File, and SHALL keep the placeholder marker `PLACEHOLDER, not benchmark-defined` out of every report generated from the Damage_Level_File.
8. THE detection and restoration specs SHALL read the Damage_Level_File as a data file and SHALL NOT import any module from `src/benchmark`.
9. IF the Damage_Level_File is missing, malformed, has an unknown field, has an unsupported `schemaVersion`, or violates criterion 4, 5, 11 or 12, THEN THE Benchmark_Suite SHALL return error `INVALID_DAMAGE_LEVELS` naming the path of the first violation, and SHALL start no run.
10. THE Benchmark_Suite SHALL provide the Cell_Damage_Models as `DamageFn` factories that a caller passes to `deriveDamagedDeck`, so that any caller (including a test of another spec) can reproduce a benchmark-damaged deck from a seed and a Damage_Level without importing the Benchmark_Runner.
11. THE Damage_Level_File SHALL mark the Occlusion_Cover_Fraction value 0.9 as `initial-unconfirmed` until Preliminary_Experiment E-2 records its confirmation or revision. E-2 SHALL validate the value by checking, on rendered occluded cards, that cells whose Cell_Window coverage is at least the fraction are never classified observed-absent by detection, and SHALL report separately the rate at which cells whose Cell_Window coverage is below the fraction are forced to `unknown` by detection. E-2 SHALL fix no pass or fail percentage, and this criterion SHALL introduce no new acceptance threshold in the Threshold_Register.
12. THE Damage_Level_File SHALL define the Occlusion_Extent (`occlusionCoverage`) per Damage_Level as a documented cap on the fraction of the readable Cell_Windows of one card that the `occlusion` model may damage. THE Occlusion_Extent SHALL be strictly below full-card coverage (less than 1) at every Damage_Level, SHALL be non-decreasing from `none` through `heavy`, SHALL equal zero at `none`, and SHALL be an initial value confirmed or revised by E-2 and marked `initial-unconfirmed` until then. THE Benchmark_Suite SHALL reject as a general starting condition any parameterisation in which the occluded cells form about 90% of all cells of a card or deck.
13. THE Benchmark_Suite SHALL provide a unit and property check that the Occlusion_Extent of each Damage_Level is below 1 and monotone, and that, FOR ALL seeds and cards, the fraction of occluded cells recorded in the Damage_Mask of an Item does not exceed the documented Occlusion_Extent cap of the Damage_Level of that Item.

### Requirement 8: Separation of system inputs and ground truth

**User Story:** As a researcher, I want the inputs given to the system stored apart from ground truth and damage masks, so that leakage is impossible by construction and detectable by test.

#### Acceptance Criteria

1. THE Dataset_Builder SHALL write System_Inputs and Ground_Truth_Artifacts as physically separate artifacts in separate directories, so that no file contains both.
2. THE Dataset_Builder SHALL store, as Ground_Truth_Artifacts, the Clean_Ground_Truth, the Damage_Mask, the Family_Key and the split role of each Item, and SHALL NOT embed any of these in a System_Input.
3. THE Dataset_Builder SHALL give each System_Input a neutral Item identifier that encodes no truth, no damage level, no Pattern_Family and no split role.
4. THE Benchmark_Runner SHALL construct each `RestorationInput` and each `detect` call from System_Inputs only, using functions whose parameter types cannot carry a Ground_Truth_Artifact.
5. THE Benchmark_Runner SHALL load Ground_Truth_Artifacts only in the comparison step, after the system under test has returned its output.
6. THE Benchmark_Suite SHALL provide a leakage test that runs `runInference` on two clean decks that differ only in the masked cells' true values and asserts deeply equal outputs, reusing the restoration masking contract.
7. THE Benchmark_Suite SHALL provide a boundary test that fails when a module under `src/vision` or `src/restore` imports from `src/benchmark`, when a module in the evaluation-input construction path imports a module that reads a Ground_Truth_Artifact, or when a System_Input directory contains a file named or typed as ground truth.
8. THE Benchmark_Suite SHALL provide a test that reads every System_Input file of a quick dataset and asserts that it contains no Family_Key, no Pattern_Family name, no Damage_Level name and no true bit value outside the damaged deck itself.
9. IF a System_Input fails the checks of criterion 8, THEN THE Benchmark_Runner SHALL return error `LEAKAGE_DETECTED` naming the artifact, and SHALL start no evaluation.

### Requirement 9: Determinism, seeds, versioning and digests

**User Story:** As a maintainer, I want fixed seeds and configuration to reproduce byte-identical outputs, so that a result can be audited by anyone.

#### Acceptance Criteria

1. THE Benchmark_Suite SHALL produce byte-identical Dataset_Manifests, damaged decks, images, Benchmark_Reports and exported tables for identical Dataset_Version, configuration, seeds and component versions.
2. THE Benchmark_Suite SHALL use no `Math.random`, no `Date`, no network request and no environment-dependent value in any function that produces a dataset or a report, and SHALL take every seed from the configuration.
3. THE Benchmark_Suite SHALL derive the seed of each Family, Item and Damage_Model from the dataset root seed and the identifying keys through a documented, deterministic function, so that adding a Family does not change the seeds of existing Families.
4. THE Dataset_Manifest SHALL record the dataset version, the Damage_Level_File version, the generator version, the root seed, every derived seed, every parameter set, the Machine_Profile identifier, and for every artifact its relative path, byte length and content digest with its algorithm name.
5. THE Dataset_Manifest and every Benchmark_Report SHALL be written as canonical JSON (stable key order, two-space indent, `\n` line endings, finite numbers only, no timestamps), and SHALL carry a `format` marker and an integer `schemaVersion`.
6. THE Benchmark_Suite SHALL compute a manifest digest and a report digest over the canonical text without the digest field, and SHALL record the algorithm name beside each digest.
7. THE Benchmark_Suite SHALL verify, before an evaluation, that every artifact in the manifest exists and matches its recorded digest, and SHALL return error `DATASET_DIGEST_MISMATCH` naming the first mismatching artifact.
8. THE Benchmark_Suite SHALL regenerate a dataset from its manifest and compare every artifact digest, and SHALL return error `DATASET_NOT_REPRODUCIBLE` naming the first differing artifact.
9. THE Benchmark_Suite SHALL write wall-clock durations, hardware descriptions and browser or Node versions to a separate runtime file that is excluded from every digest and every determinism comparison.
10. WHERE the detection pipeline documents that results may differ across environments, THE Benchmark_Report SHALL state that byte-identical reproduction is guaranteed within one runtime environment and is checked across environments only by the detection cross-environment comparison.

### Requirement 10: Splits by design family and split roles

**User Story:** As a researcher, I want splits made by original design family and a sealed test role, so that near-identical damaged copies never inflate results and nothing is tuned on evaluation data.

#### Acceptance Criteria

1. THE Dataset_Builder SHALL assign each Deck_Family, identified by its Family_Key, to exactly one Split_Role: `tuning`, `calibration`, `held-out` or `test`.
2. THE Dataset_Builder SHALL assign every Item derived from a base design, including every damaged copy, every damage-level variant and every rendering, to the Split_Role of its Deck_Family.
3. THE Dataset_Builder SHALL NOT split Items of one Deck_Family across Split_Roles, and SHALL NOT assign Items to roles at random.
4. THE Dataset_Builder SHALL assign Families to roles by a documented deterministic rule that is stratified by Pattern_Family and Profile, so that each role contains at least the documented minimum number of Families of each Structure_Label, and SHALL return error `SPLIT_STRATUM_TOO_SMALL` naming the stratum when the configured sizes cannot satisfy that minimum.
5. THE Dataset_Builder SHALL treat two base designs as one Deck_Family when they share a Pattern_Family, parameters and base-deck seed, and SHALL define the group key so that different damage seeds of one design share a Family_Key.
6. THE Benchmark_Suite SHALL provide a test that, FOR ALL generated datasets, no Family_Key and no base-deck content digest appears in two Split_Roles.
7. THE Benchmark_Suite SHALL use the `tuning` role for parameter and threshold selection, the `calibration` role only for fitting a calibration mapping and measuring prior frequency and reliability, the `held-out` role for preliminary evaluation and for experiments that check a frozen configuration, and the `test` role only for the final reported results.
8. THE Benchmark_Runner SHALL refuse to read any Item of the `test` role unless the caller passes an explicit option and the Threshold_Register is in state `frozen`, and SHALL record the option and the register state in the Benchmark_Report.
9. THE Benchmark_Suite SHALL ensure that no npm test script and no default Execution_Profile reads the `test` role.
10. THE offline tuning and calibration scripts SHALL refuse to read the `held-out` and `test` roles, and SHALL refuse a calibration split that equals or overlaps the tuning split, consistent with the restoration calibration rule.
11. IF a read of a forbidden role is requested, THEN THE Benchmark_Suite SHALL return error `SPLIT_ROLE_FORBIDDEN` naming the requester and the role, and SHALL read no data of that role.
12. THE Benchmark_Report SHALL list the Split_Role, the number of Families and the number of Items behind every Metric_Value.

### Requirement 12: Metric framework, uncertainty and undefined values

**User Story:** As a reviewer, I want every metric defined formally with explicit handling of empty groups and with uncertainty, so that no number is silently wrong.

#### Acceptance Criteria

1. THE Benchmark_Suite SHALL define every metric as a function from an Evaluation_Group of cells to a Metric_Value, with its formula, its group, its handling of abstention and its undefined conditions documented in `docs/benchmark-metrics.md`.
2. THE Benchmark_Suite SHALL return `{undefined, reason}` when a metric's denominator is zero, when the group is empty, when an input is invalid, or when a required quantity is missing, and SHALL NOT return `0`, `1` or `NaN` in those cases.
3. THE Benchmark_Suite SHALL restrict every defined rate, accuracy, precision, recall, coverage and calibration value to the closed interval [0, 1], and every Brier score to [0, 1], for inputs whose probabilities lie in [0, 1].
4. THE Benchmark_Suite SHALL report with every Metric_Value its numerator, denominator, the number of cells, the number of Items and the number of Families behind it.
5. THE Benchmark_Suite SHALL compute a confidence interval for each reported rate by a Cluster_Bootstrap with a fixed seed from the configuration, a default of 1,000 resamples (permitted range 200 to 10,000), and a 95% percentile interval.
6. THE Benchmark_Suite SHALL return interval status `not-estimated` with the reason `INSUFFICIENT_FAMILIES` when the evaluation group contains fewer Families than the documented minimum (default 5), and SHALL NOT report a point estimate as if it were an interval.
7. THE Benchmark_Suite SHALL document that the Cluster_Bootstrap resamples Deck_Families because cells and Items within a Family are correlated, and that the resulting interval describes variation across generated designs and not variation across historical cards.
8. THE Benchmark_Suite SHALL report differences between two systems on the same Items as a paired Cluster_Bootstrap difference with its interval, and SHALL mark a difference as `not-distinguishable` when the interval contains zero.
9. THE Benchmark_Suite SHALL treat a cell that the system leaves unresolved (an Abstention, an `ambiguous` or `unknown` cell) as not correct in metrics named "over all", and SHALL report the matching "over answered" metric separately with its coverage.
10. THE Benchmark_Suite SHALL name every Evaluation_Group explicitly in the report, and SHALL NOT merge groups with different damage levels, profiles, tracks or Split_Roles in one Metric_Value unless the Metric_Value is marked pooled and lists its constituents.

### Requirement 13: Detection metrics

**User Story:** As a researcher, I want hole-detection precision, recall and accuracy, so that the detector is measured against known cell values.

#### Acceptance Criteria

1. THE Benchmark_Suite SHALL define, for the Detection_Track, the positive class as hole present, derived from the Clean_Ground_Truth bit through the polarity recorded in the Detection_Result.
2. THE Benchmark_Suite SHALL report hole-detection precision as the number of cells with Condition `observed`, proposed value hole present and truth hole present, divided by the number of cells with Condition `observed` and proposed value hole present.
3. THE Benchmark_Suite SHALL report two recall values: recall over answered cells (true positives divided by truth-positive cells with Condition `observed`), and recall over all cells (true positives divided by all truth-positive cells, so that `ambiguous` and `unknown` cells count as misses).
4. THE Benchmark_Suite SHALL report hole-detection accuracy over answered cells (correct `observed` values divided by `observed` cells) and accuracy over all cells (correct `observed` values divided by all readable cells), together with coverage per Condition.
5. THE Benchmark_Suite SHALL report these detection metrics per Damage_Level, per Profile, per Split_Role, and for the Evaluation_Groups `all-cells`, `damage-masked-cells` (cells in the Damage_Mask) and `undamaged-cells`.
6. THE Benchmark_Suite SHALL report the alignment success rate, the Card_Quadrilateral corner error in pixels (mean and maximum) and the rate of each failure stage, using the metric definitions that detection exports for shared metrics.
7. WHEN a detection metric is also defined by the detection spec (accuracy over answered cells, accuracy over all cells, coverage, Brier score, expected calibration error, alignment success rate, corner error), THE Benchmark_Suite SHALL use the detection definition and SHALL provide a test that its value equals the value of the detection function on the same input.
8. THE Benchmark_Suite SHALL report detection Brier score and expected calibration error of Hole_Probability with the bin count stated, and SHALL label the Hole_Probability as an uncalibrated algorithmic score unless a detection calibration run is cited.
9. IF the detection result for an Item has Alignment_Status other than `aligned` or `aligned-with-warnings`, THEN THE Benchmark_Suite SHALL count every readable cell of that Item as unresolved in metrics named "over all", and SHALL exclude the Item from metrics named "over answered" with the failure counted in the alignment success rate.

### Requirement 14: Restoration metrics

**User Story:** As a researcher, I want restoration accuracy on all cells, on damaged cells, per provenance and with abstention reported, so that coverage is never hidden behind accuracy.

#### Acceptance Criteria

1. THE Benchmark_Suite SHALL define a cell as evaluated when it is a readable cell of an evaluated deck.
2. THE Benchmark_Suite SHALL report restoration accuracy on all evaluated cells as the number of cells whose Proposal_View value equals the Clean_Ground_Truth value, divided by the number of evaluated cells, with cells that have no Proposal_View value counted as not correct.
3. THE Benchmark_Suite SHALL report restoration accuracy on damaged cells (the Evaluation_Group `damage-masked-cells` taken from the Damage_Mask) over all such cells and over answered cells, together with the coverage, which is the number of damaged cells that have a Proposal_View value divided by the number of damaged cells.
4. THE Benchmark_Suite SHALL report per-provenance recovery accuracy for the provenance categories `repeat-inferred` and `symmetry-inferred` as the fraction of cells of that category whose proposed value equals the truth, with the count of cells in each category.
5. THE Benchmark_Suite SHALL report the abstention rate for damaged cells (cells without a Hypothesis divided by damaged cells) and the count of each Abstention_Reason.
6. THE Benchmark_Suite SHALL report top-k accuracy for k equal to 1 and 3 on damaged cells, where the top-3 value counts a cell as correct when any of its ranked alternatives equals the truth, and SHALL state that top-3 does not describe a single proposal.
7. WHERE whole-card recovery is enabled in the restoration configuration and evaluated, THE Benchmark_Suite SHALL report the whole-card recovery rate as the number of fully masked cards whose every readable cell has a rank-1 Hypothesis value equal to the truth, divided by the number of fully masked cards, together with the share of cells covered, and SHALL otherwise report `not-evaluated`.
8. THE Benchmark_Suite SHALL report restoration metrics per Pattern_Family, per Structure_Label, per Damage_Level, per Profile and per Split_Role, so that helpful and non-helpful conditions are visible side by side.
9. THE Benchmark_Suite SHALL report the number of times a prior produced a Hypothesis on a `non-helpful` family (false structure), and its accuracy.
10. THE Benchmark_Suite SHALL report the End_To_End_Track restoration metrics with the same definitions, and SHALL additionally report the metrics separately for cells that detection left `unknown`, `ambiguous` and `observed`.
11. IF a restoration run returns an error for an Item, THEN THE Benchmark_Runner SHALL record the Item, the error code and the Item's group in the report, and SHALL count every cell of the Item as not correct in metrics named "over all" and exclude the Item from "over answered".

### Requirement 15: Confidence calibration and reliability data

**User Story:** As a researcher, I want calibration error, Brier score and reliability-diagram data, so that confidence is shown to be calibrated or not.

#### Acceptance Criteria

1. THE Benchmark_Suite SHALL define, for restoration, a prediction as a cell with a rank-1 Hypothesis, its confidence as the Hypothesis_Confidence, and its outcome as 1 when the proposed value equals the truth and 0 otherwise.
2. THE Benchmark_Suite SHALL compute the Brier score as the mean of the squared difference between confidence and outcome over predictions, and the expected calibration error as the sum over equal-width bins of the bin weight times the absolute difference between mean confidence and observed accuracy, with a default of 10 bins (permitted range 2 to 50) stated in every report.
3. THE Benchmark_Suite SHALL report the Brier score and the expected calibration error both for the raw confidence and for the calibrated confidence, and SHALL report the calibrated values only where a valid Calibration_Record applies, and SHALL otherwise mark them `not-applicable`.
4. THE Benchmark_Suite SHALL write Reliability_Data per Evaluation_Group with, for each bin, its lower and upper bound, the number of predictions, the mean confidence and the observed accuracy, and SHALL mark a bin with zero predictions as empty and not as zero accuracy.
5. THE Benchmark_Suite SHALL fit a calibration mapping only on the `calibration` role, SHALL report calibration error only on the `held-out` role or, after the register is frozen, on the `test` role, and SHALL NOT report a calibration error measured on the data that fit the mapping as a result.
6. THE Benchmark_Suite SHALL write calibration data in a form that the restoration `CalibrationRecord` format accepts (method `histogram-binning`, 10 bins, split identifiers, sample size per bin, seed, benchmark version, expected calibration error with its bin count, valid prior kinds and support range), and SHALL write the record through the restoration `validateCalibrationRecord` function before saving it.
7. WHERE the synthetic-prior warning applies to a Hypothesis, THE Benchmark_Suite SHALL report its confidence as `uncalibrated` and SHALL keep the warning flag in the Evaluation_Group labels.
8. FOR ALL predictions with confidence 1 and outcome 1, THE Benchmark_Suite SHALL compute a Brier score of 0 and an expected calibration error of 0.
9. THE Benchmark_Suite SHALL state in every report that calibration measured on synthetic data does not establish calibration on historical cards.

### Requirement 16: Baselines and paired comparison

**User Story:** As a judge, I want the system compared with simple baselines that have no deck-level priors, on the same inputs and splits, so that the value of the priors is measured and not assumed.

#### Acceptance Criteria

1. THE Benchmark_Suite SHALL define exactly three comparison Baselines with a formal rule each: `B1 deck-majority` (every target receives the majority bit of all Trusted cells of the deck), `B2 column-majority` (every target receives the majority bit of the Trusted cells at the same `readIndex` in the other cards), and `B3 nearest-neighbour` (every target receives the value of the nearest Trusted cell by `readIndex` distance within the same card).
   - Note: `B0 abstain-all` is removed from the Baseline set and retained only as a test fixture (criterion 9). The labels B1, B2 and B3 are kept unchanged.
2. THE Benchmark_Suite SHALL resolve ties and missing support in each Baseline by a documented fixed rule that does not use a seed, and SHALL record a cell with no support as unresolved.
3. THE Benchmark_Suite SHALL document that `B2` uses information of other cards but no repeat-period or symmetry structure, so that the comparison between the proposed system and `B2` isolates the value of the repeat and symmetry priors over simple cross-card information. THE Benchmark_Suite SHALL document that the three Baselines are distinct comparisons: `B1` is a global density prior, `B2` is a cross-card position prior without repeat-period or symmetry structure, and `B3` is a local spatial copy within one card that tests whether local copying suffices for isolated cells and short runs.
4. THE Benchmark_Runner SHALL evaluate every Baseline (B1, B2 and B3) and the proposed system on the identical Items, the identical System_Inputs, and the identical Split_Roles, and SHALL fail with error `BASELINE_SPLIT_MISMATCH` if the Item sets differ.
5. THE Benchmark_Suite SHALL implement the Baselines in `src/benchmark` as pure functions that receive only the damaged deck, and SHALL NOT use any Ground_Truth_Artifact.
6. THE Benchmark_Runner SHALL report for each Baseline the same metrics as for the proposed system (requirement 14), and SHALL report the paired difference of accuracy on damaged cells between the proposed system and each of B1, B2 and B3 with its paired Cluster_Bootstrap interval.
7. THE Benchmark_Runner SHALL report the comparison at the system's coverage and at full coverage, and SHALL state that a Baseline that answers every target and a system that abstains differ in coverage.
8. THE Benchmark_Suite SHALL report the comparison per Structure_Label, so that a gain on `helpful` families and a loss or no gain on `non-helpful` families are both visible.
9. THE Benchmark_Suite SHALL provide an abstain-all predictor (no value proposed for any target) only as a test fixture, SHALL use it to verify that an empty prediction group yields Metric_Value `undefined` with a non-empty reason and coverage 0, and SHALL NOT include it in the Baseline set, in any paired accuracy comparison, or in any reported baseline list, because it proposes no value and has no accuracy.

5. THE Benchmark_Suite SHALL document that a result applies only to the recorded Component_Stamp, and SHALL NOT compare reports with different Component_Stamps as if they were one system without a stated comparison label.

### Requirement 25: Error registry

**User Story:** As a UI and test author, I want every expected failure to have a stable, documented code.

#### Acceptance Criteria

1. THE Benchmark_Suite SHALL define one Benchmark_Error_Code registry with a stable message per code, containing at least: `INVALID_DATASET_CONFIG`, `INVALID_DAMAGE_PARAMETERS`, `INVALID_DAMAGE_LEVELS`, `DAMAGE_TOO_SEVERE`, `PATTERN_LABEL_MISMATCH`, `RENDER_OUT_OF_LIMITS`, `SPLIT_STRATUM_TOO_SMALL`, `SPLIT_ROLE_FORBIDDEN`, `LEAKAGE_DETECTED`, `DATASET_DIGEST_MISMATCH`, `DATASET_NOT_REPRODUCIBLE`, `BASELINE_SPLIT_MISMATCH`, `REAL_DATA_NOT_LICENSED`, `INVALID_STUDY_RESULT`, `LIMIT_EXCEEDED`, `BUDGET_EXCEEDED`, `OUTPUT_DIRECTORY_INVALID`, `REPORT_TOO_LARGE`, `COMPONENT_VERSION_UNSUPPORTED`, `INVALID_REPORT`, `INPUT_TOO_LARGE`, `INVALID_JSON`, `INVALID_FORMAT`, `UNSUPPORTED_SCHEMA_VERSION`, `UNKNOWN_FIELD`, `INVALID_THRESHOLD_REGISTER`, `REGISTER_NOT_FROZEN`.
2. THE Benchmark_Suite SHALL keep each code's meaning unchanged across minor interface versions, and SHALL NOT extend the domain, detection or restoration error registries.
3. WHEN a function returns an error, THE Benchmark_Suite SHALL return the domain `Result` shape with `ok`, `error.code`, `error.message` and, where relevant, `error.path`, SHALL leave every input unchanged, and SHALL return no partial result.
4. THE Benchmark_Suite SHALL document all codes in `docs/benchmark-errors.md`, and SHALL provide a test that fails when the registry and that document differ.
5. THE Benchmark_Suite SHALL provide at least one example test per code that triggers that code.

### Requirement 28: Correctness properties and test determinism

**User Story:** As a maintainer, I want property-based tests with fixed seeds, so that invariants hold and failures are reproducible.

#### Acceptance Criteria

1. THE Benchmark_Suite test suite SHALL run every fast-check property with an explicit, distinct seed constant from a block starting at 20260700 and a bounded `numRuns` of at most 200 for image-based properties and at most 500 for data-only properties, and SHALL print the seed and the shrunk counterexample on failure.
2. THE Benchmark_Suite test suite SHALL state beside each property its generator precondition, for example "for any generated profile with 3 to 12 rows and 2 to 8 columns and a deck of 2 to 12 cards".
3. THE Benchmark_Suite test suite SHALL use no `Math.random`, `Date.now` or network access.
4. THE Benchmark_Suite test suite SHALL include a determinism property that, FOR ALL dataset configurations of the `quick` profile bounds and fixed seeds, two builds produce byte-identical manifests, damaged decks, images and Benchmark_Reports.
5. THE Benchmark_Suite test suite SHALL include a metric-bounds property that, FOR ALL evaluation groups of generated predictions with probabilities in [0, 1], every defined rate, precision, recall, accuracy, coverage, Brier score and expected calibration error lies in [0, 1], and every numerator does not exceed its denominator.
6. THE Benchmark_Suite test suite SHALL include a perfect-prediction property that, FOR ALL non-empty groups in which every prediction equals the truth with confidence 1, accuracy, precision, recall and coverage equal 1 where defined, and Brier score and expected calibration error equal 0.
7. THE Benchmark_Suite test suite SHALL include an undefined-value property that, FOR ALL empty groups, groups with a zero denominator, and groups with invalid input, the returned Metric_Value is `undefined` with a non-empty reason and is never `0`, `1` or `NaN`.
8. THE Benchmark_Suite test suite SHALL include a split property that, FOR ALL generated datasets, no Family_Key and no base-deck digest is in two Split_Roles, every Item is in the Split_Role of its Family, and each role meets the documented stratum minimum or the builder returns `SPLIT_STRATUM_TOO_SMALL`.
9. THE Benchmark_Suite test suite SHALL include a baseline-fairness property that, FOR ALL evaluated Items, the proposed system and every Baseline receive deeply equal System_Inputs and the same Item set, and a Baseline's output is unchanged when the Clean_Ground_Truth of the Item is replaced by an arbitrary other deck.
10. THE Benchmark_Suite test suite SHALL include a leakage property that, FOR ALL pairs of clean decks that differ only in the masked cells' true values, the restoration output is deeply equal, and the static boundary tests of requirement 8 and 27 pass.
11. THE Benchmark_Suite test suite SHALL include a damage-model property that, FOR ALL seeds, clean decks and valid parameters, the damaged deck equals the clean deck at every cell outside the Damage_Mask, every masked cell has no value, and the Clean_Ground_Truth deck is unchanged.
12. THE Benchmark_Suite test suite SHALL include a Damage_Level_File property that the monotonicity, zero-at-`none`, distinctness and Occlusion_Cover_Fraction and Occlusion_Extent rules of requirement 7 (including 7.12 and 7.13) hold, and example tests for each of its rejection cases.
13. THE Benchmark_Suite test suite SHALL include a report round-trip property and a corruption property as stated in requirement 20.5 and 20.6, with truncation at generated cut points and seeded single-byte corruption.
14. THE Benchmark_Suite test suite SHALL include a bootstrap property that, FOR ALL fixed seeds and groups with at least the documented minimum of Families, the interval is reproducible, its lower bound does not exceed the point value, its upper bound is not below the point value, and groups with fewer Families return `not-estimated`.
15. THE Benchmark_Suite test suite SHALL include golden tests for a fixed small quick dataset: the manifest, the report, the Markdown table and the calibration artifact, committed in version control with a stated reason for any change.
16. THE Benchmark_Suite test suite SHALL include example tests for the real-photograph `not-evaluated` status, the user-comparison `not-conducted` status, a `not-set` threshold, and a refused read of the `test` role.
17. THE Benchmark_Suite test suite SHALL convert every shrunk counterexample into a permanent example test.

## Open questions requiring confirmation

- **[CONFIRM] Q1 Four split roles with a sealed test role.** Detection used a tuning and a held-out seed block, and restoration uses tuning, calibration and held-out. This document adds a sealed `test` role used once for final numbers (requirement 10). Recommended: adopt four roles. The alternative is three roles, with the held-out role doubling as the final report, which weakens the protection against repeated looking at held-out results.
- **[CONFIRM] Q2 Renderer ownership.** The benchmark owns the full renderer. The detection spec keeps its small test generator. Both read the Damage_Level_File. Recommended: as written (requirement 4). The alternative is that detection's generator moves to `src/benchmark` and detection tests import it, which breaks the dependency direction.
- **[RESOLVED] Q3 Initial values of damage levels and the Occlusion_Cover_Fraction.** Decision: the Occlusion_Cover_Fraction is a per-Cell_Window coverage fraction with initial value 0.9, marked `initial-unconfirmed` until E-2 confirms or revises it, and no new acceptance threshold is introduced (requirement 7.5, 7.11). It is not the share of cells that are occluded. That share is controlled by the separate per-level Occlusion_Extent (`occlusionCoverage`), strictly below full-card coverage and non-decreasing (requirement 7.12 and 7.13). Other per-level numeric values remain initial values set in design and confirmed by E-2.
- **[RESOLVED] Q4 Baseline set.** Decision: B1 deck-majority, B2 column-majority and B3 nearest-neighbour are kept as the comparison Baselines, because each answers a different question (global density, cross-card position without repeat or symmetry structure, local copy within a card). B0 abstain-all is removed from the Baseline set because it proposes no value, so it has no accuracy and no meaningful paired accuracy difference. It is retained only as a test fixture for undefined-metric handling (requirement 16.9).
- **[CONFIRM] Q5 Restoration track without image evidence.** The Restoration_Track passes no detection evidence, and the End_To_End_Track measures the combined effect. Recommended: as written. The alternative adds simulated hole probabilities to the Restoration_Track, which would introduce an invented evidence model.
- **[CONFIRM] Q6 User comparison.** Recommended: define the protocol and report `not-conducted`, with no time-saving number, unless a valid study is run before submission. Confirm whether a study is planned.
- **[CONFIRM] Q7 Detection evaluation scripts.** Detection tasks define `scripts/vision-eval-synthetic.ts` and `vision-eval-real.ts`. Recommended: the Benchmark_Runner is the single source of reported numbers, and those two scripts become thin wrappers over it or are removed. This changes the detection tasks and is listed under amendments.
- **[CONFIRM] Q8 Generated data location.** Recommended: generated datasets under `data/generated` excluded from version control, with manifests and digests committed under `data/benchmark`. Confirm the folder names (`structure.md` is updated first if a new top-level folder is needed; both are under the existing `data` folder).
- **[CONFIRM] Q9 Browser re-run.** Recommended: the UI only displays committed Browser_Reports and does not run the benchmark in the browser. The alternative is a browser-run quick profile, which needs a worker and a separate budget.
- **[CONFIRM] Q10 Garín versus small profiles.** Recommended: run both and report separately (requirement 3.2), using small profiles for the `quick` profile and the Garín profile for the `full` profile and the bundled journey.

## Amendments to earlier specs

These changes are required by this spec. They are listed here and are NOT applied by this document. Each needs an explicit edit of the named spec after approval.

1. **Detection requirements 21.4, 21.8 and 22.7, and design "Damage levels (placeholder interface only)".** Damage levels, the Occlusion_Cover_Fraction and accuracy-threshold handling are now defined here. The detection spec's reference to `data/synthetic/damage-levels.placeholder.json` and its placeholder marker are superseded by the Damage_Level_File of requirement 7. The data file name `data/synthetic/damage-levels.json` is kept so that detection's `loadDamageLevels` needs no change of path, but its validated field list must match requirement 7.3.
2. **Detection requirements 21.3 and 22.1, and tasks 27 (evaluation scripts).** Detection's seed-block convention (tuning `1..N`, held-out `100000..`) is superseded, for official reports, by the Deck_Family splits of requirement 10. Recommended per Q7: `scripts/vision-eval-synthetic.ts` and `vision-eval-real.ts` delegate to the Benchmark_Runner or are removed, and `scripts/vision-tune.ts` reads the `tuning` role from a Dataset_Manifest.
3. **Detection metrics.** Detection exports accuracy, coverage, Brier score, expected calibration error, alignment success rate and corner error. This spec adds precision and recall (requirement 13), which detection does not define. No detection change is required. The shared metrics must agree (requirement 13.7).
4. **Restoration tuning script and its dataset format.** `scripts/restoration-tune.ts` has a split allow-list. The allow-list must name the benchmark roles `tuning` and `calibration`, and must refuse `held-out` and `test`. The dataset format is owned by restoration (`docs/restoration-priors.md`). If the format cannot carry a Family_Key or a role, the benchmark writes one file set per role and the amendment is not needed.
5. **Restoration recovery-property constants.** Restoration's `syntheticRecoveryConditions` (maximum masked fraction, minimum repeats) are test constants of that spec. They are not changed by the Damage_Level_File. Benchmark levels exceed those conditions on purpose, and the report states which Damage_Levels lie inside the documented recovery conditions.
6. **Restoration `shortRegionBound`.** The benchmark reads this value from the restoration configuration (requirement 5.4). No change is required, but the benchmark's run-length ranges must be re-checked when the default changes.
7. **`structure.md`.** The `scripts` entry is already planned by the sibling specs. `data/benchmark` and `data/generated` are sub-folders of the existing `data` folder. If Q8 yields a new top-level folder, `structure.md` is updated first.
8. **Previous specs' "later specs" lists.** The detection and restoration specs assumed the UI spec comes before the benchmark spec. Their dependency sections should state that the benchmark is the fourth spec and the UI the fifth, and that the UI consumes the Browser_Reports.

## Non-functional bounds summary

- Execution_Profile bounds (initial values, confirmed by E-7): `quick` at most 12 Families, 24 Items, 8 cards per deck, 1,024 px images, 200 resamples, 120 s; `full` at most 400 Families, 4,000 Items, 100 cards per deck, 2,048 px images, 10,000 resamples, 60 min, 500 MiB generated artifacts.
- Browser_Report: initial maximum 2 MiB (permitted 64 KiB to 8 MiB). Report import maximum size: configurable, with a default of 16 MiB.
- Bootstrap: 1,000 resamples by default (200 to 10,000), 95% percentile interval, minimum 5 Families for an interval.
- Calibration: 10 equal-width bins by default (2 to 50).
- Failure examples: 20 per category by default.
- Acceptance thresholds: none fixed. Each is "to be set from experiment E-n" through the Threshold_Register.
- Damage-level values, stratum minima and minimum labelled real-cell counts: initial values set in design, confirmed by Preliminary_Experiments.
